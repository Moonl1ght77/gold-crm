## 为什么分批

设计稿共 67 页，加外壳、数据和检查，一次写完会超出单任务 200k 输出 token 的预算，也没法逐批验收。所以拆成 7 批：先做外壳和数据底座，再按模块组做页面，最后统一验收和同步文档。

每批的详细计划在**开工前**基于上一批的真实代码再写，存放在 `docs/superpowers/plans/`，避免按想象中的接口写出对不上的计划。第 1 批计划：`2026-10-11-gold-crm-prototype-batch1-shell.md`（已完成）；第 2 批计划：`2026-10-11-gold-crm-prototype-batch2-data-ui.md`（实施前已定的出入写在该计划开头）。

## 第 2 批要定的数据底座（写第 2 批计划时展开）

- 原料：类别、成色、计量方式（按重量／按粒＋重量／按件）、参考单价与价源、标准损耗率、是否待核。推算只看计量方式，不认原料名称。
- 原料批次 PC-001～PC-007：采购来源、单价、原量（毫克，宝石另记粒数）。
- 去向记录：成品耗用和在制由生产任务的实际用料推出；余料、回收料、确认损耗、待核对来自库存流水。检查脚本拿采购原量和推出的去向合计对账，所以平衡检查能抓到数据错误，不是自己验自己。
- 系列 A–E、款式及标准用料表；生产任务及实际用料；成品；客户（含会员标记）和业务单的骨架；审批骨架。
- 推算函数：批次平衡、单件成本（按原料类别拆开）、系列原料耗用与占比、业务单毛利、各项合计。
- 检查：编号唯一且前缀正确、引用都存在、每个批次按自己的单位平衡（宝石粒数和毫克都平）、PC-001 为 100g＝90＋5＋3＋2、PC-004 为 60 粒＝48＋10＋1＋1 且 600mg＝480＋100＋10＋10；再临时注入一种原料（铂金）和一个批次，确认推算和检查照常工作。

## 每批都要做到

- `npm run build`、`npm run check` 通过（在 `app/` 里）。
- 浏览器里本批页面在手机和桌面、深色和浅色下都点一遍，控制台没有报错；手机视图没有横向滚动。
- 页面按"列配置＋数据"写，复用通用组件；数字一律由推算函数得出，不手写。
- 内部链接一律用 `href()` 生成，检查脚本会拦手写的 `#/...`。
- 不改 `demo/`。
- 提交后推送 `origin/claude/clickable-prototype`（Joe 2026-10-11 已同意本分支推送）；按三问更新项目记忆。
- 单批输出控制在 200k token 以内；估计超了就再拆。
